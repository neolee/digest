## Fast and Hard Code

**来源**: [Fast and Hard Code](https://lucumr.pocoo.org/2026/8/22/fast-hard-code/)<br>
**作者**: Armin Ronacher

> 作者认为，LLM 让编程语言选择变得不再重要，并推动开发者转向过去较难的“硬语言”和底层技术，追求快速而小巧的软件。
> 
> - **语言选择贬值** — 熟悉一门语言本身不再关键，因为 LLM 可以改写代码，甚至让开发者使用自己完全不懂的语言。
> - **营销影响增强** — 选择语言越来越取决于“营销”；作者观察到，原本可能不会选 Rust 的人，现在开始发布 Rust 代码。
> - **风向转变** — 两个氛围变化推波助澜：更多人想要快速软件，以及 LLM 擅长在不改变行为的前提下优化代码。Mitchell Hashimoto、Charlie Marsh、Jarred Sumner、Daniel Lemire 等人都热衷性能，且对 AI 写代码持开放态度。
> - **“硬语言”受惠** — 除 Rust 外，连对 AI 颇为排斥的 Zig 社区也在受益：Cloudflare 的 Artifacts 用纯 Zig 实现 Git 协议，编译成约 100 KB 的 WebAssembly 模块；Vercel 发布小型快速的 Zig 编程智能体 fx。这些项目大多由 LLM 辅助完成。
> - **“硬技术”普及** — 开发者开始涉足 DWARF、eBPF、自定义网络驱动、自定义加密和古老硬件；这些过去对多数人不可及，有些领域（如加密）还被圈内人有意排挤。
> - **不确定性** — 作者坦言“编程已解决”的说法程度不明，并把 Rust 新用户部分归因于上述两种氛围变化，但也可能是无关的。
> 
> 实际意义在于：世界或许会出现更多“垃圾代码”，但也可能诞生更多想要把软件做得又快又小的开发者。

**点评**: 确实如此，LLM 制造的垃圾和宝藏都会不断冒出来，最终还是看驾驶员的。最近另一个有趣的案例也证明了一样的结论，Linus Torvalds 在一个颇为复杂的 debugging 任务中和 LLM 斗智斗勇，LLM 屡次提议放弃，但在他的不断 push 下最终还是解决了问题，作为“奖励”他让 LLM “执笔”写了相关的 commit 信息，然后自己在后面补了[一段感想](https://github.com/torvalds/linux/commit/818bebeb63dd6bf5f4e07e145f6cdbace520a34c)：

> 这是一场噩梦般的调试过程，AI 承担了大量繁重工作，帮了大忙。我想称它为不知疲倦的帮手，但 AI 多次直截了当地表示这不可能、无法解决，我们干脆写份报告算了。我怀疑这些东西是被那些可能不像我这么固执的人训练出来的。但尽管 AI 几次准备放弃，在我推动下，它确实不断添加调试代码并忠实地进行分析。该鼓励的还是要鼓励，所以我让 AI 写了上面的提交信息。
