## What is the quality of software that AI writes?

**来源**: [What is the quality of software that AI writes?](https://www.johndcook.com/blog/2026/08/26/what-is-the-quality-of-software-that-ai-writes/)<br>
**作者**: Wayne Joubert

> AI 编程代理写出的代码表面可读，但在作者经验中普遍存在过度冗长、抽象建模差等质量问题，可能积累大量技术债。
> 
> - **核心经验** — 作者基于对 GPT 5.5、5.6 与 Codex 的“开箱即用”使用发现，AI 生成的代码不会像混淆代码那样难懂，但常比必要代码多出 2–3 倍，且简化能力明显弱于生成能力，一次会话中写数百行用半小时、缩短简化却花了 4 小时。
> - **典型缺陷** — 代理倾向于写更多代码而非删减；文件超过一万行也不会主动拆分；会在不同模块重复发明相似函数；构造 10–20 个参数的巨型参数列表；用实现机制而非意图命名；发明读者难以理解的术语；重复同一表达式而不提取为有意义变量；硬编码“魔法常量”。
> - **潜在亮点** — 在被明确要求深入审视问题时，较强模型（GPT 5.6 Ultra）能做出贴合问题领域的良好对象设计，说明模型并非完全没有能力。
> - **改进空间与局限** — 作者预期改进 AGENTS.md 等引导文件能缓解多数问题，但不应该需要极端工程手段才能让代理写出好代码；同时作者强调自身经验难以普遍化，且未比较其他编程代理，不同代码库、语言、模型和工具链会带来差异。
> - **基准缺失** — 目前缺少一个类似 SWE-bench 的公认代码质量基准，而代码质量的许多方面本可以客观验证，作者希望前沿实验室在模型开发中纳入此类评估。
> 
> 代码质量直接影响可维护性、人工审计与代理自身的上下文效率，因此需要从基准和训练目标上真正重视，而不只追求完成任务速度。

**点评**: 和我的体验基本吻合。其实目前大部分真正深度使用 coding agent 的人的感受都差不多，差异主要体现在对未来软件工程的预测上，有人认为代码质量不再重要，但我[无法认同这一点](https://soulhacker.me/posts/good-code/)，此文作者也是。

## EVE Online: The Move to Python 3 Begins!

**来源**: [EVE Online: The Move to Python 3 Begins!](https://simonwillison.net/2026/Aug/25/eve-online-move-to-python-3/)<br>
**作者**: Simon Willison

> EVE Online 正式启动从 Python 2 到 Python 3 的迁移，这是其运行 Stackless Python 二十多年来的重大升级。
> 
> - **迁移规模** — 先用 futurize 脚本处理 240 万行代码，再人工审查约 2 万个 Python 2/3 行为差异点，如 `1 / 2` 在 Python 2 中为 0、在 Python 3 中为 0.5。
> - **历史背景** — 自 2003 年上线即运行 Stackless Python，上次重大升级是 2010 年迁至 Stackless Python 2.7。
> - **不确定之处** — 公告未说明如何替换 Stackless；但去年大会已介绍过方案：用开源的 carbonengine/scheduler 库在 EVE Frontier 的 Carbon 引擎中取代它。
> - **参考价值** — EVE Online 是 Python 大规模部署的经典案例，迁移流程对同类项目有借鉴意义。
> 
> 此次升级标志着一个近二十年的 Python 2 大型生产系统正式换代，“自动化转换加人工复核”的策略或将成为大型代码库迁移范本。

**点评**: 这标题看着简直像十几年前穿越过来的（但事实上是昨天的），EVE Online（星战前夜）的技术栈变迁（或者说 [Stackless](https://github.com/stackless-dev/stackless/wiki/) 的变迁）是 Python 发展史的一个非常独特的视角。
